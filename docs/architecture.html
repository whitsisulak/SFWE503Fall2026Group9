Software architecture description

CLMS Software Architecture

The Clinical Laboratory Management System tracks a specimen from the test order, through collection and its printed barcode, to the analyzer result that comes back carrying the same barcode. It also manages the reagent stock the lab runs on. This document describes how the current build is put together, why, and where the remaining ConOps requirements will attach.

§ 1

Overview

CLMS is a client–server system written entirely in C# on .NET 10. A single HTTP API owns every business rule and all persisted data. The user interface is written once as a component library and hosted two ways: in the browser as an installable web app, and inside native apps for iOS, macOS and Windows.

The current build is a vertical slice: one path through each architectural layer, built end to end.

  • Built: sign-in with role-based access and account lockout, reagent inventory with low-stock and expiry alerts, test orders with barcodes and sample collection, automatic ingestion of analyzer result files, and an audit trail.
  • Not yet built: billing and point of sale, reporting, patient management screens, purchase orders, the lockout email and the result-validation workflow. §10 maps each ConOps requirement to its status.

§ 3

Runtime behavior

3.1 Sign-in and an authorized request

Authentication is stateless. The API issues a signed JSON Web Token (JWT) carrying the user's name and role. The client stores the token and sends it with every call. The client reads the role only to decide which buttons to show; the API re-checks the role on every request.

3.2 Instrument result ingestion

Analyzers do not call the API. They write plain-text result files into a shared folder, following the simplified HL7 ORU format defined in ConOps 6.3.5. The barcode printed on the tube at collection comes back as the first field of every line, and that barcode is how a machine result finds its test order.

One line of an analyzer result file

1234Barcode: matches TestOrder.Barcode
|
TestMessage type
^
B123Test ID → TestCode
^
T3 UptakeDescription
|
28Value, stored as text (“28” or “Absent”)
|
202208221340yyyyMMddHHmm, read as UTC
§ 4

Data model

Six tables in PostgreSQL, mapped by Entity Framework Core from Clms.Api/Domain/Entities.cs. Every primary key is a GUID generated by the application before the row is saved, so an audit entry can reference a new order's ID in the same transaction that creates it.

4.1 Test order lifecycle

  1. 0 · OrderedOrderedCreated by POST /api/test-orders with a generated 6-digit barcode.
  2. 1 · CollectedCollectedA specimen collector marks the sample collected. A second attempt returns 409.
  3. 2 · InProgressIn progressDefined, not set by any code yet.
  4. 3 · ResultedResultedSet by the ingestion worker when the first matching result arrives.
  5. 4 · ValidatedValidatedReserved for the result-validation workflow.

§ 7

Design decisions

The choices that shape the rest of the system, with what each one costs. Open any row for the rationale.

D-01Write the UI once, in a component library, and host it twice

DecisionAll pages, layout and client services live in Clms.Ui. The web and native projects only register services and mount Routes.

WhyThe course team needs a browser app and native apps without maintaining two UIs.

CostHost-specific styling needs a home outside the library; the stylesheet is currently copied into both hosts.

D-02Put every business rule behind one HTTP API

DecisionClients never touch the database. Components depend on the IClmsApi interface, implemented over HTTP.

WhyOne place enforces roles, lockout and audit logging, whichever client is used.

CostEvery screen needs the API reachable; there is no offline data.

D-03Share C# contracts instead of generating clients

DecisionRequest and response records live in Clms.Shared, referenced by both sides.

WhyA contract change breaks the build on both sides at once, with no code-generation step.

CostOnly .NET clients benefit; a non-.NET client would use the OpenAPI description instead.

D-04Stateless JWT with the role inside the token

DecisionSign-in returns an HS256 token with name and role, valid for 480 minutes. One authorization policy per role; the lab manager passes all of them.

WhyNo session store to run, and the same token works for the browser and native apps.

CostA role change or lockout doesn't affect a token already issued until it expires. There is no revocation.

D-05Receive analyzer results from a polled folder

DecisionA background service inside the API scans instrument-drop/ every 5 seconds, following the file format in ConOps 6.3.5.

WhyFile-change notifications are unreliable across Docker bind mounts and network shares; polling works everywhere.

CostUp to 5 seconds of latency, and only one API instance may run the worker or files are processed twice.

D-06Generate primary keys in the application

DecisionEntities assign Guid.NewGuid() and EF Core is told keys are never database-generated.

WhyAn audit entry can reference a record's ID before the first save.

CostThe EF configuration is required: without it, results added to an existing order were sent as UPDATEs and ingestion failed.

D-07Store result values as text

DecisionTestResult.Value is a string.

WhyAnalyzers send quantitative (“28”) and qualitative (“Absent”) values in the same field.

CostReference-range checks and numeric reports will need to parse values per test code.

D-08Create the schema on startup (temporary)

DecisionThe API calls EnsureCreated and seeds demo data on first boot.

WhyA new team member can run the system with no database setup steps.

CostThe schema cannot evolve. Switch to EF Core migrations before the next model change.

D-09Cache the web app shell, never the data

DecisionThe PWA service worker caches the app's static files and always sends /api/ requests to the network.

WhyLab results and stock levels must be current; a stale result is worse than no result.

CostThe app opens without a connection but shows no data.

§ 8

Security

Authentication

  • Passwords hashed with PBKDF2-SHA256, 100,000 iterations, 16-byte random salt, compared in constant time.
  • Account locks after 5 consecutive failures and returns 423 until a lab manager unlocks it.
  • An unknown username and a wrong password both return 401.
  • Tokens are checked for signature, issuer clms-api, audience clms-clients and expiry, with 1 minute of clock skew.

Authorization

  • Inventory and order routes require a signed-in user at the group level.
  • Restricted actions add a role policy on the endpoint (§5).
  • AuthorizeView hides controls the role can't use, for usability only.

Audit trail

  • Written for AccountLockedOut, AdjustStock, CreateTestOrder, CollectSample and ResultReceived, in the same transaction as the change.
  • Not yet written for successful sign-ins or account unlocks. No screen displays the log.

Configuration and transport

  • CORS admits only the configured client origins.
  • Development runs over plain HTTP. The JWT signing key and database password are in checked-in config, acceptable only for development.
  • The web client keeps the token in localStorage, where any script running on the page can read it.
